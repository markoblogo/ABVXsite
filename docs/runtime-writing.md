# Runtime Writing publisher

Status: engine implementation; **activation and production publication require a verified configured private store**. The feature flag defaults off. No public admin UI, user login, new collection or project/book-card publisher is introduced.

## Normal operation after activation

1. Retain existing OS `publication begin` → intake → inspect → source-specific owner approval → handoff. Drafts and original photographs stay private. The packet must contain exact approved JSON-frontmatter Markdown and hashed web image descriptors.
2. Run `npm run content:runtime -- publish --packet /private/packet.json --request-id <stable-id> --output /private/receipt.json` for offline preparation; add `--write` to publish. This writes content data through `/api/writing/manage`. It does not run Git, tests, build, PR review or deployment. Image conversion to an approved web derivative remains preparation, not generative editing.
3. Report the returned canonical URL. **The owner opted out of routine automatic public-result checks on 2026-10-26.** `STORED` confirms atomic promotion of the content snapshot, not a checked browser page. The owner can inspect the result. `content:runtime-verify` is optional; never fabricate `PUBLISHED_VERIFIED`, indexing or test PASS from a storage receipt.
4. Import the receipt and authenticated export into the existing OS runtime adapter. Book Readiness reads a regenerable ignored projection of this source. Continue existing follow-up enrollment without inventing a page observation. Projection/OS failure queues reconciliation; it never causes a new publication or request ID.

The CLI saves the exact retry command before sending it, the storage receipt, and a private `.export.json` containing authoritative sources and discovery metadata. Keep these under ignored operational exports. Do not send source prose or credentials to Cortex. There is deliberately no runtime-success entry in the legacy Git/QA process-learning cohort.

`status` returns current revisions. `update` requires `--packet` and `--expected-revision`; `rollback --id <slug> --to-revision <old> --expected-revision <current>` and `unpublish --id <slug> --expected-revision <current>` require a stable request ID, `--write` and a private receipt path. Updates cannot change the canonical identity or first publication date. First-addition time is stored separately: new backfilled articles enter the current feed when actually added; seeded registry timestamps and unknown historical anchors are preserved. An ambiguous timeout must reuse the saved command and request ID; `409` requires inspecting the current revision rather than blind overwrite. `export --output /private/export.json` can resume an interrupted projection without writing content.

Supported fast writes are existing **native Writing** articles, notes, build logs, reviews and Kitchen Notes recipes, including illustrations and native video companions. Existing Working Stories remain readable/searchable through their established adapter; their separate write schema and scheduled Psychology pools stay on the legacy route until explicitly migrated. Cards, categories and new rendering components remain later engineering work.

## Storage and read contract

One private Vercel Blob store holds immutable content snapshots and approved image bytes. A single `writing-v1/head.json` points at a SHA-256-checked snapshot. Snapshot uploads precede conditional `ifMatch` pointer promotion; initial creation refuses overwrite. Competing writers get a conflict. Request IDs bind exact command hashes, so retries return the original receipt. Failed uploads/conditional writes leave harmless private orphan objects and never partly publish an article.

The current private pointer is read with `useCache:false`; a bounded process cache holds only immutable, verified snapshots. React request caching keeps component readers on one snapshot. For every managed record, runtime is the sole authority. Previously unclaimed legacy slugs can continue through their existing consumer during incremental cutover; an owned record or tombstone always overrides bundled Markdown. Publishing a duplicate legacy slug is rejected. Store failure fails closed; bundled Markdown cannot resurrect edited or withdrawn articles. The initial seed retains source bytes, media paths, URLs and first dates. Later image mapping changes only frontmatter paths and is recorded alongside original/published source hashes. The authored body stays identical.

Same-origin `/media/writing/runtime/<sha256>.<ext>` serves only assets referenced by currently visible source records, checks their bytes, and sends `no-store`. Draft files and arbitrary private Blob objects are inaccessible. Runtime images bypass Next's persistent image optimizer; approved web derivatives are already prepared. Allowed formats are bounded PNG/JPEG/WebP with matching hash, signature and dimensions; no SVG, URL import or server-side arbitrary fetch. The content API accepts at most 4 MB of JSON.

Article pages, home Writing slots, Writing search/feed, Kitchen Notes, archive, video companions, sitemap, `/content-index.json` and `/llms.txt` derive native membership from that snapshot. `beforeFiles` rewrites retain the existing discovery URLs while static generated files remain build fixtures for other surfaces. Project/book/category data stays unchanged. Git content files become an archive/export for managed records, not a second editable source. Unclaimed legacy sources are included explicitly in authenticated exports so scheduled pools remain visible until their consumer migrates.

## Activation runbook — engineering operation, not a post operation

- Run normal code validation, CI/Preview, exact-head completed review and verified production deployment for the engine. The build manifest `content/runtime-writing-engine.json` fingerprints executable inputs, independent of content/feed changes. The OS engine receipt binds that fingerprint to the verified deployment; unrelated feed-only deployments do not require qualifying a new engine. Do not claim the manifest itself is deployment evidence.
- Inspect actual project access, existing stores, tariff and limits before provisioning. Never assume the store is free. Use a **private** store and server-only credentials; do not print credentials. Bind publishing credentials and activation to Production only; Preview must not write Production content. No public `NEXT_PUBLIC_` secrets or credential in a URL. The publisher token is a random secret of at least 32 characters; compare hashed Bearer values in constant time. It grants content CRUD only, not Git/deploy/account access.
- With `RUNTIME_WRITING_ENABLED` still off, initialize once: `npm run content:runtime -- seed --initialize` with operator Blob access. Initialization refuses an existing head. Compare seed sources and normalization/index parity with the accepted archive. The seed is migration, not a new publication, follow-up anchor or independent timing trial.
- Configure `RUNTIME_WRITING_ENABLED=1`, private Blob access (`BLOB_READ_WRITE_TOKEN`, or the supported store/OIDC configuration) and `RUNTIME_WRITING_PUBLISH_TOKEN`, then deploy the engine normally. Reuse the existing provider verification. Install the authenticated source projection for OS/Radar. Existing scheduled pools may create unclaimed legacy slugs during incremental cutover; they cannot replace a managed runtime record. Switch each legacy consumer explicitly before managing its posts through the API. Keep other content surfaces on their existing route.
- Test a new slug after build, retry, stale writer, update, rollback, withdrawal, failed upload/store, media, discovery/search and mobile on an isolated backend. `npm run qa:runtime-writing` does this with synthetic content on localhost only. The supplied Framewright post is authorized as a real pilot once Production is activated; do not publish it through Git and call that a runtime pilot. Routine post-result browsing remains owner-optional.

`RUNTIME_WRITING_BACKEND=file` plus `RUNTIME_WRITING_DIR` is **local acceptance only** and is rejected on Vercel. It is never a durable Production fallback. Default flag-off operation retains the old archive.

Recovery: use content revisions/conditional rollback. Do not simply disable runtime mode after new writes: that would expose an obsolete Git archive. First reconcile/export every current source, media mapping and tombstone into an explicitly reviewed recovery snapshot. Retain immutable history and request receipts; garbage collection and hard deletion are outside this MVP.

## Verification limits

Local acceptance is not proof of Blob account access or public activation. Storage receipts are not Search Console processing/indexing evidence. No automatic book production, KDP action, market research or new scheduler is triggered. Latency and cost savings remain unmeasured until real completed operations exist; the engineering build/test time is separate from post-publication latency.
