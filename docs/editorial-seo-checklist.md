# Editorial SEO release checklist

Use this for public-content releases, including editorial guides linked from Focus, Systems, Books, or other core pages. The command gate matches `.github/workflows/ci.yml`; SEO and visual checks depend on the change.

1. **Start from current source.** Use a clean existing ABVXsite checkout when suitable; otherwise use an isolated checkout/worktree. Fetch `origin/main` and branch from it; never mix unrelated changes. Use the `codex/` branch prefix for Codex work. Treat `content/editorial/` and `content/editorial/index.json` as source; preserve published slugs.
2. **Map the page before drafting.** List every requested heading and article once. For translations, pair entries with the same `translationGroup`, the correct `language` (`en` / `uk` / `fr`), and localized `linkLabel`; keep one canonical route per language.
3. **Write and connect each guide.** Record `publishedAt` and `updatedAt` in the editorial index from actual publication/substantive changes; never derive them from build time. Use optional `seoTitle` to distinguish a guide from its related catalogue without changing its displayed heading. Maintain static page update dates in `content/pages.json` when their content or metadata changes. Add Markdown with a title matching the index entry, a distinct search intent, useful project/book links, and no unsupported claims. Add the default-language link beside its exact page heading; the article route supplies language links and alternate metadata.
4. **Regenerate public indexes.** Run `npm run llms:generate`; commit the generated `public/llms.txt` and `public/content-index.json`. Do not hand-edit generated output. Re-run the generator after the build if it changes either file.
5. **Verify locally before opening one PR.** Use `npm ci` for a fresh checkout or changed dependencies/lockfile; resolve installation/audit failures before publication. Then run `npm run content:validate`, `npm run ecosystem:check`, `npm run lint`, `npm run test:sync`, `npm run cortex-abv:vector-export:check`, `npm run build`, then `npm run qa:seo` after the build, and `npm audit --omit=dev --audit-level=high`. Confirm generator/build output introduces no unexpected changes and include intended generated files in the same PR. No unrelated refactoring or repeated broad checks after success.
6. **Verify the release.** Wait for all PR checks and Vercel Preview; merge only after they pass. Confirm the production deployment is `READY` for the merge SHA, then open the changed catalogue/core page and representative detail/article routes. Check section links, language switching where applicable, sitemap alternates, and public indexes. For external links, verify destination and new-tab attributes; for UI changes, check mobile wrapping/overflow and actual player behavior where applicable. Search Console processing/indexing remains a separate check.

Operational evidence and build-skip boundaries: [publication/performance audit](performance-and-release-audit.md). The release receipt includes check durations; production verification remains separate.
